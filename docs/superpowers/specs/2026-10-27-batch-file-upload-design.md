# 批量文件上传接口设计

## 目标

在不改变现有单文件上传接口的前提下，新增一个支持批量上传的接口。批量请求必须全量成功或全量失败，不返回部分成功结果。

## 接口契约

- 路径：`POST /api/files/batch`
- Content-Type：`multipart/form-data`
- 文件字段：多个同名 `files` 字段
- 返回：`ApiResponse<List<FileMetadataVO>>`
- 单次最多上传 10 个文件，至少上传 1 个文件
- 现有 `POST /api/files` 和 `FileService.upload(MultipartFile)` 保持不变

## 实现方案

在 `FileService` 增加批量上传方法，并由 `FileServiceImpl` 负责批量编排：

1. 校验文件数量；数量非法时直接失败。
2. 对所有文件执行现有的非空、大小、类型、文件名和签名校验；全部通过后才开始写入。
3. 按现有规则为每个文件生成对象键并写入对象存储，再保存对应的元数据。
4. 收集本批次已写入的对象和元数据，按输入顺序转换为 `FileMetadataVO` 返回。

Controller 只负责接收 `files` 并调用批量服务方法，不复制单文件校验或存储逻辑。

## 失败处理

对象存储或元数据写入任一步骤失败时：

- 删除本批次已经写入的对象；
- 删除本批次已经写入的元数据记录；
- 保留并抛出最初的异常，不返回部分结果。

清理失败不能覆盖原始异常，处理原则与现有单文件上传一致。由于对象存储和数据库属于不同资源，补偿清理是全量失败语义的实现基础。

## 测试范围

- Controller 使用两个 `files` 字段提交，验证返回两个元数据。
- 批量上传超过 10 个文件时返回校验错误。
- 任意文件校验失败时，验证对象存储没有写入。
- 第二个文件写入失败时，验证第一个文件的对象和元数据被清理。
- 现有单文件上传测试继续通过，确认旧接口行为不变。
